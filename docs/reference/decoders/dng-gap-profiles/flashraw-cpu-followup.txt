# FlashRaw CPU follow-up: post-#737/#738 baseline and rejections

Host-specific evidence for the first three FlashRaw CPU follow-up candidates.
Host: WSL2 Debian, AMD Ryzen 7 5800H, 15 visible CPUs, kernel
`6.6.87.1-microsoft-standard-WSL2`, glibc `2.41-12+deb13u3`, THP
`[madvise]`, THP defrag `[madvise]`. Do not compare timings across host
sessions.

The baseline is merged `origin/main` commit `eaf7ec6`, which contains PR #738
and the synchronized #737 10-bit compact Huffman path. Every real-file timing
used three fresh processes x five interleaved rounds. Fornax and FlashRaw 0.2.0
ran in the same session. Wall cells are median `[min-max]` in milliseconds.
Counter cells are medians per output sample. All eight inputs passed the strict
three-way Fornax/Rawler/FlashRaw dimensions, storage, bits, and pixel-equality
gate before timing.

Pentax K-5 `_MAR0543.DNG` is materialized, 18,952,092 bytes, SHA-256
`6f6419209340d07d597ccca66dc367d64cff3308ef2694c8f90c6259f3a5c431`.
It is a 4992 x 3284, 14-bit, restart-free single-scan LJPEG workload. Its 15T
wall time is effectively identical to 1T, confirming that tile-level
parallelism cannot help this motivating case.

## Fixed 12-bit packed-u32 full-difference table: rejected

The candidate used 4,096 packed `u32` entries, exactly 16 KiB per table, with
full differences for code plus magnitude lengths at most 12 bits. Longer
values retained the compact canonical lookup. A test pinned the table size and
covered short full hits, boundary codes, long codes, symbol 16, stuffing,
truncation, and invalid prefixes.

The table reduced retired instructions by about 19-23% on LJPEG and improved
the tiled files, but Pentax regressed repeatably beyond every observed range.
The 16 KiB footprint raised cycles and L1D pressure enough to increase wall
time by 16-17%. It failed the no-regression gate and was reverted.

## Component-pair refill: rejected

The candidate retained the existing refill behavior for one-component scans and
used a 54-bit first target followed by the required 32-bit compact-table target
for the second component. The latter is deliberately 32 rather than FlashRaw's
27 because Fornax's canonical fallback can consume 31 bits.

The refill-count test showed fewer boundaries, and exact equality passed, but
real two-component LJPEG regressed 8.5-14.0% at 1T. Retired instructions rose
from about 79.6 to 98.2/sample on 5D3 because the extra target checks dominated
the saved refill boundaries. It was reverted.

One-tile synthetic scans at 256 x 256 show the same direction: two-component
smooth scans rise from 0.616 ms to 0.667 ms, and two-component noisy scans from
0.613 ms to 0.687 ms. One-component scans remain effectively flat in wall time
but pay about one extra instruction/sample because the generalized refill target
does not constant-fold away.

## Decision

Do not retain either compute candidate. The post-#737/#738 compact 10-bit table
and existing 32-bit reader refill remain. The 12-bit table helps smaller tiled
files but fails the mandatory Pentax no-regression gate; component-pair refill
regresses all real LJPEG cases. No production code from these experiments
remains.

The restart-free single-scan parallelism design is recorded separately and is
stopped at its review gate. No parallel implementation was attempted.

Raw wall and `perf` files remain under `/tmp`; only this summary is committed.
